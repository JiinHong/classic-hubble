# Deterministic Collection Coverage Audit

조사일: 2026-07-11

## 질문

LLM, OCR, 이미지 인식 없이 `httpx/requests + HTML/JSON 파싱` 수준의 파이썬 스크립트로 공연 정보와 클래식 프로그램을 어느 정도 수집할 수 있는가?

## 한 줄 결론

- **공연명·날짜·장소 같은 기본 메타데이터: 95% 이상**
- **곡목이 하나라도 있는 프로그램: 전체 공연의 약 75%**
- **작품 알림에 바로 사용할 수 있는 완전한 프로그램: 약 71%**
- **프로그램을 이미 공개한 공연만 분모로 보면: 약 82%**

따라서 Classic Hubble의 현실적인 표현은 `단순 파이썬 수집기로 전체 프로그램의 약 70~75%를 확보할 수 있다`이다. 하나의 범용 BeautifulSoup 규칙이 아니라 사이트별 결정론적 어댑터를 만든다는 전제다.

## 포함·제외 범위

### 포함

- 일반 HTTP 요청
- HTML 텍스트 파싱
- `img alt` 파싱
- 페이지 소스에 포함된 Vue/JSON 상태 파싱
- 정규식 또는 DOM 선택자를 이용한 프로그램 영역 분리
- 리디렉션 처리와 URL 정규화

### 제외

- 이미지 픽셀 읽기
- OCR
- 멀티모달 LLM
- 이미지의 글자를 사람이 입력하는 작업
- 곡목이 없는 페이지에서 제목만 보고 프로그램을 추론하는 작업

PDF의 텍스트 레이어를 `pypdf`로 읽는 것은 LLM이 아닌 결정론적 파싱이지만, 사용자의 질문에서 파일 인식을 제외했으므로 주 결과에서는 제외했다. 참고 수치로만 별도 표시한다.

## 계산 기준

기존 조사에서 12개 사이트 계열의 2026년 공연 상세·티켓 공지 48건을 확인했다. 이 표본은 시장 전체를 무작위 추출한 통계 표본이 아니라, 일반 사례와 이미지 전용·미정·변경 같은 예외를 함께 포함한 엔지니어링 표본이다.

| 주 표시 형태 | 건수 | 이미지 인식 없는 처리 |
|---|---:|---|
| 완전한 HTML 프로그램 | 31 | 가능 |
| 부분 HTML 프로그램 | 2 | 가능하지만 `partial` 처리 필요 |
| PDF 중심 | 1 | 질문의 주 결과에서는 제외 |
| 이미지 + 완전한 alt | 3 | 가능 |
| 이미지 전용, alt 없음 | 7 | 불가능 |
| 이미지 전용, 곡목 자체 없음 | 1 | 어떤 인식 방법으로도 불가능 |
| 미정·당일 공개·아직 미게시 | 3 | 원문 자체에 데이터 없음 |
| **합계** | **48** |  |

## 결과

### 1. 사이트별 어댑터가 있는 단순 파이썬

HTML 33건과 완전한 alt 3건을 합치면 다음과 같다.

```text
36 / 48 = 75.0%
```

여기에는 완전한 프로그램과 `외`, `등`이 붙은 부분 프로그램이 함께 들어 있다. 부분 프로그램 2건을 제외하고 작품 알림에 바로 쓸 수 있는 완전한 목록만 계산하면 다음과 같다.

```text
34 / 48 = 70.8%
```

따라서 제품 계획에서는 다음처럼 잡는 것이 안전하다.

- 최소 출시 기대치: 65~70%
- 어댑터 안정화 후 기대치: 70~75%
- `75% 이상을 항상 보장`한다고 외부에 약속하면 안 됨

### 2. 프로그램을 실제로 공개한 공연만 계산

48건 중 4건은 프로그램이 실제 미정이거나, 상세 이미지를 읽어도 곡목 자체가 없었다. 이 4건을 빼면 공개된 프로그램은 44건이다.

```text
36 / 44 = 81.8%
```

즉, **주최 측이 프로그램을 공개하기만 했다면 약 82%는 이미지 인식 없이 가져올 수 있었다.** 나머지 7건, 15.9%는 alt 없는 이미지 전용이었다.

이 숫자는 수집기 성능을 평가할 때 유용하지만, 사용자에게 보여 주는 전체 공연 커버리지로 사용하면 안 된다. 사용자는 프로그램 미정 공연도 서비스에서 보게 되기 때문이다.

### 3. PDF 텍스트 파싱까지 허용

텍스트 레이어가 있는 PDF 1건을 결정론적으로 읽는 경우:

```text
37 / 48 = 77.1%
37 / 44 = 84.1%  # 프로그램 공개 공연만 분모로 사용
```

PDF 처리의 증가는 이번 표본에서는 2.1%p에 불과했다. 초기 파이프라인에서 우선순위가 높은 것은 PDF보다 HTML·JSON·alt 어댑터다.

### 4. 하나의 범용 HTML 파서만 사용하는 경우

사이트별 Vue 상태나 특수 필드를 파싱하지 않고, 화면에 바로 있는 텍스트와 alt만 읽는 범용 파서는 대략 **60~70%** 수준으로 보는 것이 맞다.

롯데콘서트홀과 부천아트센터의 일부 프로그램은 페이지 소스의 Vue `data` 객체 안에 이스케이프된 HTML로 들어 있다. 브라우저 실행은 필요 없지만, 해당 JSON을 읽는 도메인 전용 코드가 필요하다.

## 일반 공연 메타데이터와 프로그램의 차이

`공연 정보`를 공연명, 날짜, 장소, 포스터, 가격, 출연자, 예매 링크까지 넓게 부르면 비율이 훨씬 높다.

| 데이터 | 단순 파이썬 예상 커버리지 | 이유 |
|---|---:|---|
| 공연명·날짜·장소 | 95~100% | KOPIS와 각 상세 페이지에 거의 항상 존재 |
| 가격·관람등급·러닝타임 | 90~95% | 미정·무료·공지 단계에서는 일부 누락 |
| 출연자 | 85~95% | 이미지 프로필만 있는 예외가 있음 |
| 예매 URL·포스터 URL | 95% 이상 | URL 자체는 HTML/JSON에서 얻을 수 있음 |
| 프로그램 일부 이상 | 약 75% | HTML·JSON·alt 합산 |
| 완전한 프로그램 | 약 71% | 부분 공개와 미정 제외 |

따라서 KOPIS 기반 공연 목록 서비스는 LLM 없이도 거의 전부 만들 수 있다. LLM 또는 OCR이 필요한 지점은 `공연 자체를 수집하는 일`이 아니라 `이미지에만 있는 곡목과 연주자 정보를 구조화하는 일`이다.

## 권장 결정

1. 첫 단계는 LLM 없이 사이트별 파이썬 어댑터를 만든다.
2. 우선순위는 NOL, 예술의전당, 세종문화회관, 롯데콘서트홀, 금호아트홀, 부천아트센터, 아트센터인천 순으로 잡는다.
3. HTML, Vue JSON, alt에서 확보한 프로그램만 `confirmed` 또는 `partial`로 저장한다.
4. 이미지 URL만 얻은 공연은 `image_pending`으로 남기고 곡목을 추론하지 않는다.
5. `not_published`, `announced_later`, `selected_on_day`를 null과 구분한다.
6. 초기 제품은 약 70%의 확정 프로그램으로 시작하고, 사용자에게 정보 출처와 상태를 표시한다.
7. 실제 운영 로그가 쌓인 뒤 이미지 전용 비중이 충분히 클 때 OCR/LLM 파이프라인을 추가한다.

## 해석상의 한계

- 48건은 예외를 의도적으로 포함한 목적 표본이므로 엄밀한 시장 점유율 통계가 아니다.
- 사이트 개편과 공연 등록 주체에 따라 비율은 변한다.
- 같은 사이트에서도 기획공연과 대관공연의 입력 방식이 다르다.
- `프로그램이 페이지에 존재한다`와 `작품 alias DB에 정확히 정규화된다`는 별개의 성공 지표다.
- 운영 커버리지는 페이지 접근 실패, 차단, 변경 감지 지연 때문에 조사 시점 수치보다 낮아질 수 있다.

이 한계를 반영해 Classic Hubble의 계획 수치는 단일한 75%가 아니라 **초기 65~70%, 안정화 후 70~75%**로 두는 것이 적절하다.
